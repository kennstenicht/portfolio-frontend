# Project conventions

Ember 6 + Vite app (Embroider, strict resolver, WarpDrive, CSS Modules) that ships
as a prerendered static site. Generic Ember/Glimmer guidance lives in
`.agents/skills/ember-best-practices/` — this file only covers what is specific to
this app.

## HTML attribute ordering (Glimmer templates)

Apply this order in `.gts` template markup:

1. Glimmer args (`@route`, `@model`, etc.)
2. `class`
3. Semantic/functional HTML attrs (`type`, `href`, `rel`, `target`, `role`, etc.)
4. ARIA attrs (`aria-label`, `aria-hidden`, etc.)
5. Data-test attrs (`data-test-*`)
6. Modifiers (`{{on ...}}`, etc.)

## BEM + CSS Modules class naming

Class names are generated by `vite.config.mjs` via `css.modules.generateScopedName`.
In **dev/test** they are human-readable; in **production** they are replaced by a
`_<sha256 slice>` hash. Never hardcode a class name in markup or in a test — always
go through `getBem`.

### Naming formula (dev/test)

Given `app/components/application/header/styles.module.css`:

1. `relativePath` = dirname relative to project root → `app/components/application/header`
2. `moduleName` = filename stem before the first `.` → `styles`
3. `blockClass` = relativePath with substitutions (first occurrence only, then `/` → `-`):
   - `app/` → dropped
   - `components` → `c`
   - `routes` → `r`
   - `assets/styles/objects` → `o`
   - `assets/styles/utils` → `u`
4. If `moduleName !== 'styles'`, append `-${moduleName}` (used for the object modules,
   e.g. `objects/link.module.css` → `o-link`).
5. Per CSS key:
   - Default: `${blockClass}__${localName}` → `c-application-header__navigation`
   - If `localName.startsWith('scope')`: `${blockClass}${localName.replace('scope', '')}`
     → `c-application-header` (for `scope`) or
     `c-application-header--is-navigation-open` (for `scope--is-navigation-open`)

Examples: `app/routes/page/styles.module.css` → `r-page`,
`app/components/project-detail/mint-ec/styles.module.css` → `c-project-detail-mint-ec`,
`app/assets/styles/objects/link.module.css` → `o-link`.

### `getBem` helper (`app/utils/get-bem.ts`)

```ts
const bem = getBem(styles); // or getBem([styles, otherStyles])

bem(); // styles['scope']            → 'c-application-header'
bem('navigation'); // styles['navigation']       → 'c-application-header__navigation'
bem({ 'is-navigation-open': true }); // scope + scope--is-navigation-open
bem('link', { active: true }); // link + link--active
bem({ style: project.id }); // scope + scope--style-<id>  (string modifier value)
bem({ variant: ['a', 'b'] }); // scope + scope--variant-a + scope--variant-b
```

In templates: `{{bem "navigation"}}`, `{{bem (hash is-navigation-open=this.isOpen)}}`,
`{{bem "link" (hash active=isActive)}}`.

A missing key logs `[bem] class "…" not found in CSS module` in development — that
warning means the CSS module and the template drifted apart.

### Global styles

`app/assets/styles/` is ITCSS-layered (`settings/`, `generic/`, `elements/`) and
imported by `app/assets/styles/styles.css`, which `app/app.ts` imports. There are no
CSS `<link>` tags in `index.html` and fonts are bundled — do not add either back.
Reusable multi-component blocks live in `assets/styles/objects/*.module.css` and are
pulled into a component module with
`composes: scope from "/app/assets/styles/objects/link.module.css";`.

## Content as a static JSON:API

Editorial content is Markdown in `content/pages/` and `content/projects/`. The
`static-json-api` Vite plugin (`static-json-api.js`, configured in `vite.config.mjs`)
compiles it to a static JSON:API under `public/api/<type>s/`:

- One file per record → `public/api/<type>s/<id>.json`, plus a combined `index.json`.
- `<id>` is the Markdown filename without `.md` (`content/projects/mint-ec.md` → `mint-ec`).
- **Frontmatter → `attributes`** (parsed with `gray-matter`).
- **Body → the `contentAttribute`**, rendered to HTML with `marked`. Both `page` and
  `project` use `content`. HTML in frontmatter and body is allowed and rendered
  as-is (e.g. `<br>` in a title).

`public/api/**` is a build artifact — gitignored, **never hand-edit it**. The dev
server regenerates it on add/change/unlink of a source `.md`; a clean checkout
produces it at `buildStart`.

Records are consumed via WarpDrive; schema + fetch helpers live in
`app/data/<type>.ts`. **A field added to frontmatter must also be added to that
schema's `fields` and to the TS interface** or it is invisible to the app.

`ssg-routes.mjs` discovers prerender routes from the content **source** directories
(`contentRouteIds('pages')`, `contentRouteIds('projects')` — directory names, not the
resource type), so adding a Markdown file also adds its prerendered route with no
route list to edit. Top-level content pages resolve through the `page` route
(`/:page_id`), so a new `content/pages/foo.md` is live at `/foo` immediately.

## Routes live in `app/routes/`, and the strict resolver needs a registry

Routes are pod-style: `app/routes/<route>/{route.ts,template.gts,styles.module.css}`.
The app uses `ember-strict-application-resolver`, which does an exact key lookup
(`routes/page`, `templates/projects/show`), so `app/modules.ts` is the registry:

- `normalizePodModules` strips the `routes/` prefix and maps `*/route` → `routes/*`
  and `*/template` → `templates/*`. Anything under `app/routes/` that is neither is
  ignored.
- `app/services/**` is globbed in automatically.
- **Addon services injected by name** (`@service intl`, `cookies`, `keyboard`,
  `-ea-motion`) must be registered by hand — the glob only covers this app's services.
- **Addon components that addons invoke by name from their own templates** must be
  registered by hand too (all the `ember-animated` ones).
- This app's own components, helpers, and modifiers are imported directly in `.gts`
  files and must **not** be registered.

Adding a route means: an entry in `app/router.ts`, a folder under `app/routes/`, and —
if it should be prerendered — an entry in `staticRoutes` in `ssg-routes.mjs`. A
missing-module resolver error at boot usually means something needs a `modules.ts`
entry.

## Static prerendering (SSG)

`vite-ember-ssr` prerenders every route from `ssg-routes.mjs` at `vite build` and
writes the HTML into `dist/`, using the `<!-- VITE_EMBER_SSR_HEAD -->` /
`<!-- VITE_EMBER_SSR_BODY -->` markers in `index.html`.

- Two app entries: `app/app.ts` (browser, imports the CSS and the inspector support)
  and `app/app-ssr.ts` (prerender, exports `createSsrApp` plus `settled` so the
  renderer can await the run loop and WarpDrive's test waiters). Both share
  `app/modules.ts`. Keep `modules.ts` free of side-effect imports.
- `app/entry.ts` uses `bootRehydrated`, not `Application.create()` — a plain create
  would boot a second interactive copy next to the prerendered DOM.
- **No browser globals at module-evaluation time.** The prerender runs in HappyDOM;
  anything an addon touches while its module evaluates must be polyfilled in
  `app/ssr-polyfills.ts`, which must stay the _first_ import of `app-ssr.ts` (this is
  why `ember-animated`'s module-level `new DOMRect(...)` works). Guard SSR-only code
  with `import.meta.env.SSR` so Vite strips it from the client bundle.
- Data during prerender is served off disk by `SsgFileHandler`
  (`app/utils/ssg-file-handler.ts`), registered ahead of `Fetch` in
  `app/services/store.ts`. It only handles **root-relative** GET URLs, so request
  helpers in `app/data/*.ts` must keep using `/api/...` paths, not absolute URLs.
- `vite-ember-ssr@0.4.1` is **patched** (`patches/vite-ember-ssr@0.4.1.patch`) to add
  named exports to its CJS-in-SSR shim. Bumping the version means refreshing the
  patch, not just the range.

## i18n

`ember-intl` with `translations/{en,de}.yaml` (plus `components/` and `routes/`
subfolders). Translations are added and the locale is set in
`app/routes/application/route.ts#beforeModel` (currently `en`). `no-bare-strings` is
enabled in `.template-lintrc.js`, so user-facing copy goes through `t`; add
`{{! template-lint-disable no-bare-strings }}` only for deliberate exceptions.

## SEO

`app/components/seo/metadata` renders `<title>` and the OG/Twitter tags into
`document.head` via `{{#in-element}}`. Every route template that is a page should
render it. `host` and `siteName` come from `app/config/environment.ts`; titles are
lowercased by design.

## Adding a project

1. **Content** — `content/projects/<id>.md`: frontmatter (`title`, `subtitle`,
   `excerpt`, `facts`, `tags`, `position`, `previewImage`, `visible`, `metaTitle`,
   `metaDescription`) + body → `content`. This alone gives you the data, the
   `index.json` listing entry, and the prerendered `/projects/<id>` route.
2. **Assets** — under `public/assets/projects/<id>/`.
3. **Detail component (optional)** — the detail page picks a content component by
   project id from `CONTENT_COMPONENTS` in `app/components/project-detail/index.gts`,
   falling back to `Default`. For a custom layout add
   `app/components/project-detail/<id>/index.gts` + co-located `styles.module.css`
   and register it in that map.

## Testing

Tests run in a real browser (QUnit + Testem, Chrome headless), not jsdom, so
stylesheet CSS is applied and `assert.dom(...).hasStyle(...)` works.

- `pnpm test` = `vite build --mode test && ember test --path dist`. There is no watch
  runner: append `--server` (`pnpm test --server`) for an interactive run.
- The QUnit page is also served by the dev server at `/tests` (`pnpm start`).
- **The test-page settings live in the bootstrap, not in the config.**
  `tests/test-helper.ts` sets `autoboot: false`, `rootElement: '#ember-testing'` and
  `locationType: 'none'` itself, because `app/config/environment.ts` can only see
  the build mode and the dev server always builds `development` — a mode check
  there misses the page served at `/tests`. Without `autoboot: false` the
  application boots into `<body>` and renders the real app (routed from the
  `/tests` URL, so the error page) on top of the QUnit UI, and its route-level
  `<Metadata>` writes tags into `document.head` that break the `seo/metadata`
  integration tests.
- Build the suite with `--mode test` regardless: that is what makes
  `config.environment === 'test'`, quiets the app logs, and keeps development-only
  branches (e.g. `AnimatedTools`) out of the run.
- `tests/index.html` links no CSS or JS of its own. App styles arrive through the
  module graph (`app.ts` imports `styles.css`); qunit and `#ember-testing-container`
  styles come from `ember-qunit`'s own imports. Do not re-add
  `/@embroider/virtual/{vendor,app,test-support}.{css,js}`: the two CSS bundles are
  empty, `app.css` is not emitted at all (it 404s), and the JS bundles only set
  legacy globals (`runningTests`, the macros runtime config) that nothing in this
  build reads.
- Because production hashes class names, select by role/text or `data-test-*`
  attributes — never by a BEM class.
- Layout: `tests/acceptance`, `tests/integration`, `tests/unit`; use the wrappers in
  `tests/helpers/index.ts`, not `ember-qunit` directly.

## Commands

pnpm only (Node ≥ 20.19, CI on 22).

- `pnpm start` — dev server on :4200
- `pnpm build` — production build + prerender into `dist/`
- `pnpm lint` / `pnpm lint:fix` — css, format, hbs, js and **types** (`ember-tsc`) in
  parallel
- `pnpm test`

CI (`.github/workflows/ci.yml`) runs `pnpm lint` and `pnpm test`.

## Commits

`Type(Scope): Subject`, e.g. `Feat(SSG): Prerender routes with vite-ember-ssr`,
`Refactor(Styles): Bundle fonts and drop legacy virtual CSS/JS links`.
